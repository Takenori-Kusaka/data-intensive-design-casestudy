# 題材 C：共通基盤の費用と性能（結果）

このファイルは `cs/c/aggregate.py` が `results/c/*.jsonl` から作る。表の数は結果のファイルから数えたもので、手では書いていない。性能の数字は、同じ機械・同じデータの中での相対比較で、ほかの環境には一般化できない。製品どうしの優劣は断定せず、どの問い合わせの形で、どちらに差が出たかを書く。

問い：ログ基盤・分析基盤で、どの持ち方が何を払うか。題材は、架空の宅配注文サービスの注文イベントのログ（1 行が 1 イベント、23 列）。構成は **N**（素朴な作り：行指向の表に、製品の既定のまま型つきで取り込み、INSERT で流し直し、DELETE で古い行を消す）、**B**（共通の基準：再実行しても同じ結果になる取り込み）、**BE**（基準＋題材 C の重点：E-C1 列指向と圧縮、E-C2 取り込み時に型を決める列と後から読む列を分けて検査する、E-C3 保持期間をパーティションの単位で落とす）。

### スキーマが揺れたとき、失敗はどこに出るか

30,000 行（7 項目）の NDJSON の、後ろの 6,000 行だけ形を変えた。取り込んだあと、揺れた項目を読む人が 1 行ずつ何を得るかを、生成器の正解（上流が意味していた値）と比べた。続けて、その項目の合計と平均を素直な問い合わせで取り、正解と比べた。JSON のまま持つ作りでは、変換できない値を NULL にする寛容な問い合わせも試した。

## 期待どおりにならなかった結果・気づいた点

- **ClickHouse 26.8 は、設定の表示では async_insert=1 が既定だった**（system.settings の値：1）。1 行ずつの INSERT は、既定のままだと 1 要求あたり約 61 ms かかり（まとめ書きを待つ時間）、async_insert=0 では約 5.6 ms だった。wait_for_async_insert=0 では応答は早いが、応答の直後に読めた行は 330〜460 行（500 行中）で、書き込みの完了より前に応答が返る。パーツの数は、測った時点ではマージが進んでいて 1 行 1 パーツの状態は見えなかった
- **キーでない列の絞り込み（顧客 1 人、全列）は、列指向でも行指向の全走査と同じ桁だった**：L で PostgreSQL 134 ms、ClickHouse 75.6 ms、DuckDB＋Parquet 48.2 ms。集計ほどの差は出ていない。キーで 1 行の検索は、索引のある PostgreSQL が 0.48 ms、ClickHouse は 73.0 ms（event_id は並び順の 2 番目で、索引として効かない）
- **ClickHouse の JSON 型は、文字列で送った日時を DateTime として持った**。最初に書いた問い合わせ（`doc.ts.:String`）は、エラーにならずに全行 NULL を返し（読めた行 0）、日ごとの集計の照合で不一致になって気づいた。型を指定した部分列（`.:型`）は、型が違う行を黙って NULL にする
- **寛容な読み方は、エラーを消す代わりに、黙って違う値を返す**：変換できない値を NULL にする集計が、エラーなしで正解と違う値を返したのは 14 実行（ClickHouse：json、DuckDB：auto、DuckDB：auto_full、DuckDB：parquet_files、DuckDB：parquet_union、PostgreSQL：jsonb）。数字の文字列（"1200"）に変わっただけでも、ClickHouse の `.:Int64` は 1 実行で合計が減った
- **ClickHouse の JSON 型の値を `::Float64` で変換すると、項目の無い行が 0 になった**：3 ケース（フィールドが消える（delivery_fee）、フィールドが増える（tip）、値が null になる（amount: null））で、合計は正解と同じだが、平均は 182.1（正解 227.6）、60.0（正解 300.0）、3069.7（正解 3837.1） になった。行そのものは NULL として読める（表の ○）のに、変換した集計だけが変わる
- **ClickHouse の既定の型つきの取り込みは、欠けた項目と null を 0 で埋めた**（3 ケース：フィールドが消える（delivery_fee）、名前が変わる（amount → total_amount）、値が null になる（amount: null））。このうち 2 ケースは合計が正解と同じ値のままで、平均だけが違った（182.1（正解 227.6）、3069.7（正解 3837.1））。列を Nullable にしていない、よくある定義での結果
- **DuckDB の read_json は、整数の列に来た小数をエラーにせず丸めた**（read_json に列の型を指定して表へ、同上（ignore_errors=true）、read_json の自動判定で NDJSON を直接読む（既定の sample_size）、バッチごとの Parquet を read_parquet で読む（既定）：6000 行）。PostgreSQL の jsonb_populate_record と ClickHouse の JSONEachRow は、同じ入力で取り込みを止めた
- **DuckDB の read_json の自動判定は、既定では先頭の行だけを見て型を決める**。揺れが 24,000 行目より後ろにあると、型の違う値で読み出しがエラーになり（1 ケース）、増えた項目は列として現れなかった（1 ケース）。sample_size=-1（全行から判定）では、型の混じった列が JSON 型になり、素直な合計は関数の型のエラーになった
- **PostgreSQL の COPY の ON_ERROR ignore が飛ばしたのは、型に変換できない値の行だけ**（2 ケースで各 6000 行を黙って落とす）。列の数が違う行と NOT NULL の違反では、指定していても取り込み全体が止まった（3 ケース）
- **DELETE は容量を減らさない**。PostgreSQL は DELETE の後も VACUUM の後も 240.2 MB・240.1 MB（前は 240.2 MB）で、VACUUM FULL（2897 ms（2814 ms〜3039 ms）。表を排他ロックして書き直す）で 160.0 MB になった。ClickHouse の軽量な削除も、直後は 73.8 MB のままで、OPTIMIZE FINAL の後に 49.2 MB。DuckDB の表は、DELETE と CHECKPOINT の後、ファイルが 46.9 MB → 52.2 MB と大きくなった
- **ClickHouse は、落とした後も古いパーツをしばらくディスクに残す**：有効なパーツの容量は減ったが、使わなくなったパーツが 76.2 MB〜221.6 MB 残っていた（測定の時点。実際に空くまでの時間は測っていない）
- **ReplacingMergeTree は、そのまま読むと重複が見える**：同じ入力を 2 回流した後、ふつうの SELECT では重複 20000 行、3 日目を足した後も 20000 行。FINAL を付けるか OPTIMIZE FINAL の後は 0 件。訂正で入力から消えた行は、FINAL でも 100 行残った
- **ClickHouse のブロックの重複排除（non_replicated_deduplication_window）は、まったく同じブロックにしか効かない**：同じ入力の 2 回目は重複 0 行、訂正後の入力では 19900 行、半分で止まった後の流し直しでは 10000 行。既定（window=0）では同じ入力でも 20000 行
- **DuckDB の索引は、この絞り込みでは使われなかった**：実行計画は索引なしと同じ Ungrouped Aggregate → Projection → Seq Scan で、ファイルだけが 48.0 MB → 76.8 MB に増えた
- **Kafka を間に置いても、読む側の Collector が既定のままだと、Kafka は「下流が戻るまでためる場所」にならなかった**：読む側はメッセージを先に読み出して印を付け、自分のメモリのキューで再試行する。その Collector を強制終了すると 820 件を失い、保持（2 秒）を超える停止では逆に 0 件だった（もう Kafka の外にあったため）。処理の後で印を付ける設定にすると強制終了では失わないが、保持を超えた分は 780 件を失った
- **Collector のキューがあふれると、新しい要求は HTTP 503 で断られた**（660〜1400 件。メモリでもディスクでも起きた）。受け付け済みで届かなかったログは 0 件。失うかどうかは、断られた送り手が再送するかで決まる（この実験の送り手は再送しない）。障害の間に送った 800 件より多く断られた試行が 5/6 あり、下流が戻った後の要求も、キューが空くまでは断られた
- **正常時に届くまでの遅れ**：届くまでの p50 は、メモリのキュー 0.95 ms（0.93 ms〜0.96 ms）、ディスクのキュー 8.50 ms（8.18 ms〜8.72 ms）、Kafka を挟み処理の後で印を付ける設計 1.24 ms（1.22 ms〜1.28 ms）。ディスクのキューは fsync を指定している。差の内訳は分けて測っていない。受け口は同じ機械の上の実験用の HTTP サーバーで、ネットワークの遅れは無い
- **ブローカーの一時停止の後、同じログが 2 回届いた**（20 件）。失ってはいないが、受け手に重複を捨てる仕組みが要る

## 見送り

- **全文検索の専用ストア**（OpenSearch など）：入れていない。失うのは、ログの本文（message）を語で探す検索と、その索引。題材 C のログの問い合わせは、決まった列の絞り込みと集計だけにした。見直す条件：本文の語での検索が日常の問い合わせになり、列の絞り込みで絞ってからの走査では応答時間が足りなくなったとき。入れる場合は、転置索引の更新の費用（ガイド Part 5）と、導出ストアとしての作り直しの手順（Part 12）が加わる

## 限界

- 1 台（8 コア、WSL2 の Docker）の上の、1 ノードの製品。データは 100,000・1,000,000・3,000,000 行（CSV で 17.9 MB〜542.0 MB）で、どの規模もメモリに収まる。時間と容量は、この機械・この大きさでの相対比較で、絶対値は一般化できない。メモリに収まらない規模、複数ノード、同時に多数の利用者がいる状態は測っていない
- 問い合わせは暖機 1 回のあとの 7 回で、OS のページキャッシュは捨てていない（この環境ではキャッシュを捨てる操作をしない決まり）。冷えた状態の時間は測っていない
- 時間はクライアントで測った。PostgreSQL は psycopg、ClickHouse は HTTP と JSON の応答、DuckDB は同じプロセスの中で、経路が違う。数 ms 以下の差は、経路の差と区別できない
- 製品の設定は、メモリの上限のほかは既定のまま。ClickHouse と DuckDB は 8 スレッド、PostgreSQL の並列ワーカーは 1 つの問い合わせに 2 つまでで、使う CPU の数が違う。並び順・索引・型（ClickHouse の LowCardinality など）は、それぞれの製品でふつうに書く形を 1 つ選んだもので、選び方で結果は変わる
- データは生成器が作った一様に近い分布（店舗と商品だけ偏りを付けた）で、実際のログの偏りや長い本文は無い。圧縮の効き方はデータに強く左右される
- 取り込みは、サーバーが手元のファイルを直接読む形。ネットワーク越しの取り込み、少しずつ届くデータの取り込みは、C-1 の 1 行ずつの書き込みと C-5 の 100 行ずつの挿入だけ
- C-2 の揺れは 8 ケースで、ネストした構造、配列、日時の形式の変化は入れていない。CSV で流したのは PostgreSQL だけ。BE の検査の決まり（必須の項目、整数だけを通す）は実験の前に決めた 1 つの形
- C-3 の保持は 1 回の操作の時間と容量だけ。落としている間のほかの読み書きへの影響、VACUUM FULL のロックの間の停止は測っていない
- C-4 は 1 つの書き手が順に流す形で、同時に 2 つの実行が走る場合、流し直しの途中で読む人が見るものは測っていない
- C-6 の時間は縮めた（再試行の上限 120 秒と 3 秒、保持 2 秒）。下流の「停止」は 503 の応答で、接続の拒否や無応答ではない。送り手は再送しない。Kafka の役は Redpanda の 1 ノードで、Apache Kafka では流していない
- 「0 件」「失わなかった」は、この手順と試行回数で起きなかったという意味で、起きないことの証明ではない
