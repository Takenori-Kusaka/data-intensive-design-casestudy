# 題材 A：基盤をまたぐデータ統合（結果）

このファイルは `cs/a/aggregate.py` が `results/a/*.jsonl` から作る。表の数は結果のファイルから数えたもので、手では書いていない。性能の数字は同じ環境の中での相対比較で、ほかの環境には一般化できない。

問い：注文の状態の変化を、検索の索引と通知へ、失わず・重複させず・順序を崩さずに届けられるか。構成は 3 つ：**N**（二重書き込み。受け手は冪等でない）、**B**（アウトボックス＋ポーリング、冪等な受け手）、**BE**（アウトボックス＋Debezium の CDC、冪等な受け手、キーは注文 ID）。

### 言葉の決め

| 言葉 | 数え方 |
| --- | --- |
| 応答済み | 注文サービスが呼び出し元に成功を返した要求。N は「DB のコミット」と「ブローカーの確認応答」の両方が済んだとき、B・BE は DB のコミットが済んだときに成功を返す |
| 失敗した要求 | 呼び出し元に成功が返らなかった要求（発行の時間切れ、強制終了で応答なし）。正規の要求が失敗した数として数える |
| 正にあって届かない | 記録のシステム（注文の表の履歴）にコミットされているのに、受け手の状態に 1 回も効いていないイベントの数。最後まで待った後の最終状態で数える |
| ブローカーのログ内の重複 | トピックを先頭から読み直し、同じイベント ID が 2 回以上あった余分の数 |
| 届いた重複 | 受け手に 2 回以上渡されたイベントの、余分の回数（受け手が渡されるたびに 1 行記録する） |
| 状態に 2 回効いた | 受け手の状態を 2 回以上変えたイベントの、余分の回数。索引は上書きの回数、通知は送信の履歴の行数 |
| 順序の入れ替わり | 同じ注文について、索引に効いた順（初めて効いたときだけを見る）が、記録のシステムのコミットの順（版）と逆になった隣り合う組の数 |
| 古いイベントの再適用 | 同じ注文について、索引に効いた順（再送で 2 回目に効いたものも含む）で、版が下がった隣り合う組の数 |
| 最終状態の食い違い | 最後まで待った後、索引の最後のイベントが、注文の表の最後のイベントと違う注文の数（索引に無い注文を含む） |
| 遅れ | 注文サービスが DB のコミットを終えた時刻から、索引に初めて効いた時刻まで。同じホストの時計。試行ごとの p50・p95 の中央値 |

数の書き方：「**12**（3/5 試行）」は、試行の合計が 12 で、5 試行のうち 3 試行で 1 件以上起きたことを表す。「a／b」は索引の受け手／通知の受け手。

### 見送り：Kafka のトランザクション（「厳密に 1 回」）

Kafka のトランザクションは使わず、受け手の冪等性（イベント ID を、効果と同じトランザクションで処理済みの表に入れる）だけにした。B・BE（変種と除去を除く）の全 85 実行の合計：ブローカーのログ内の重複 1461、届いた重複 索引 1551／通知 1551、**状態に 2 回効いた 索引 0／通知 0**、正にあって届かない 索引 0／通知 0。見送りで失うもの：ブローカーのログには重複が残る（ログを直接読む別の受け手は、自分で重複を捨てる必要がある）。見直す条件：受け手の状態を持てない（処理済みの表を効果と同じトランザクションで書けない）受け手が加わるとき。

## 期待どおりにならなかった結果・気づいた点

- 二重書き込みの順序の入れ替わりは起きたが、頻度は低い（並行度 16 で応答済み 10000 件に対し 5 組）。同じ注文への 2 つ目の更新は、1 つ目のコミットまで行のロックで待たされるので、入れ替わるのは「1 つ目がコミットしてから発行するまで」に 2 つ目がコミットと発行を済ませたときだけである。最終状態の食い違いはさらに少なく、試行によっては 0 だった。少ないから安全とは言えない：エラーが出ないので、照合なしでは 1 件も見つからない

- Redpanda のコンテナイメージは、引数なしでは開発用の設定で起動した（write_caching_default＝true、--unsafe-bypass-fsync）。ガイドの Part 8 の注記（開発モードは write caching が既定で有効で、fsync も省く）のとおりで、欠落を数える実験では明示して切る必要があった

- ブローカーのトピックの自動作成を切ると、Debezium のハートビート用のトピック（__debezium-heartbeat.<prefix>）が作られず、コネクタは RUNNING のままイベントの発行が止まった（開発中に観測。結果のファイルには入れていない）。コネクタの設定に topic.creation.default.* を入れて、Kafka Connect にトピックを作らせた

- ブローカーの強制終了（docker kill）では、応答済みのメッセージは失われなかった（Redpanda：応答済みなのにブローカーのログに無い 0 件、Apache Kafka：0 件）。プロセスだけを止める障害では OS のページキャッシュが残るので、fsync の有無の差は出ない。電源断に当たる障害（ホストごと落とす）は試していない（未検証）


## 限界

- 1 台の上の、1 ノードのブローカーと 1 台の PostgreSQL。複製・フェイルオーバー・リージョンをまたぐ障害は入っていない

- 1 回の実行は 2000 件・注文 200 件と小さい。発生率は、この負荷・この機械・この実装（Python のスレッド、librdkafka の既定の linger.ms＝5 ms）でのもので、一般化できない

- 受け手は役割ごとに 1 プロセスで、全パーティションを固定で割り当てた（コンシューマーグループのリバランスは起きない）

- 導出側の PostgreSQL は synchronous_commit=off にした（受け手が書き手に追いつけるようにするため。導出側は落としていない）

- 遅れと応答時間は、同じ環境の中の相対比較。絶対値に意味は無い

- Kafka Connect のオフセットの記録の間隔は 10000 ms にした（既定は 60000 ms）。再送による重複の件数はこの間隔に比例して変わる

- 障害を外す合図は、件数に加えて経過秒数も使った（ブローカーが止まっている間、B・BE の書き手は止まらず、件数だけでは障害の長さを決められないため）

- 「防いだ」「0 件」は、この手順と試行回数で起きなかったという意味で、起きないことの証明ではない


## 未検証

- Kafka のトランザクション（「厳密に 1 回」）を使った構成（見送り。受け手の冪等性だけの結果を上に示した）

- 発行を先にして DB の更新が失敗する型（DB にない出来事が流れる）

- ブローカーや DB のホストごとの停止（電源断に当たる障害）、ディスクが実際に埋まるまでの WAL の増加

- Debezium のフェイルオーバー用のスロット（slot.failover）、プライマリの切り替えをまたぐ CDC

- CDC の落とし穴（A-L1〜L3）の Apache Kafka での照合（Redpanda だけで流した）

- アウトボックスの行を送信後に消す運用での、スロット喪失後の取り直し（この実験では行を消していない）

- クラウドのマネージド製品（マネージドの Kafka・CDC）
