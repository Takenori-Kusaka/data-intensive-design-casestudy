# ケーススタディの設計（実験の前に決めること）

作成日：2026-11-18。ガイド `data-intensive-design-guide`（256 枚）の主張を、手元の 1 台（WSL2 の Docker）で確かめる。ガイドの「ケーススタディ」の注記（題材 A〜D で測ると書いた点）を、漏れなく測る対象にする。

## 1. 題材の世界：架空の宅配注文サービス

会社・サービス・数値はすべて架空で、実在の組織とは関係がない。

| 種類 | 名前 | 持つデータ | 実装 |
| --- | --- | --- | --- |
| 業務サービス | 注文（orders） | 注文と状態（受付 → 調理中 → 配達中 → 完了／取消）。記録のシステム | Python の小さなサービスと PostgreSQL |
| 業務サービス | 在庫（inventory） | 店ごとの在庫数。記録のシステム | PostgreSQL（題材 D では MySQL・CockroachDB でも） |
| 業務サービス | 決済（payments） | 支払いの記録。記録のシステム | PostgreSQL |
| 業務サービス | 通知（notifications） | 送信の履歴。イベントの受け手 | イベントの消費者 |
| 共通基盤 | イベント基盤 | 注文のイベントのログ | Redpanda（照合に Apache Kafka） |
| 共通基盤 | 検索・分析 | 注文の索引、集計。導出データ | ClickHouse、DuckDB＋Parquet |
| 共通基盤 | ログ基盤 | サービスのログ。スキーマが揺れる | PostgreSQL（jsonb）、ClickHouse、DuckDB |

認証・AI・セキュリティの各基盤は組まない（ガイドの Part 13 で扱い、未検証と明記済み）。

データは生成器から作る（乱数の種を固定）。正解（どの注文がどの状態で終わるべきか、どのイベントが届くべきか）も生成器から作り、実験の出力からは作らない。

## 2. 結論の型

- 構成：**N**（素朴。よくある作り）、**B**（共通の基準）、**BE**（基準＋題材ごとの重点）
- **除去実験**：B・BE から要素を 1 つずつ外し、何が再び壊れるかを表にする
- **正常な操作も混ぜる**：基準を入れたせいで、正規の処理が止まる・遅くなる・失敗することも数える（基準の費用）
- **見送り**：入れない要素には、何を失うかと、見直す条件を書く
- 測っていないことは「未検証」。件数は結果のファイルから数える

### 共通の基準（B）の候補（6 要素）

| # | 要素 | 効く題材 | 対応するガイドの Part |
| --- | --- | --- | --- |
| B1 | 記録のシステムを 1 つに決め、ほかは導出データとして作る | A・B | 3 |
| B2 | 二重書き込みをしない（同じトランザクションでアウトボックスに書く） | A | 6 |
| B3 | 受け手を冪等にする（イベントの ID で重複を捨てる） | A・B | 11 |
| B4 | スキーマの互換性検査を通してから配る（推移的な検査） | B | 7 |
| B5 | 応答済みの書き込みを失わない複製の設定（同期） | D | 8 |
| B6 | 導出データを作り直す手順と前提条件（保持・スナップショット）を持つ | B | 12 |

### 題材ごとの重点（E）の候補

| 題材 | 重点 | 見送りの候補（代償を測る） |
| --- | --- | --- |
| A | E-A1 キーごとの順序を保つ（同じ注文は同じパーティション）、E-A2 CDC の受け手の停止を検知して WAL の上限を設ける、E-A3 定期的な照合（正と導出の差を数える） | Kafka のトランザクション（「厳密に 1 回」）は見送り：受け手の冪等性で足りるかを測る |
| B | E-B1 expand-contract（3 段階）で DB のスキーマを変える、E-B2 新旧の導出ストアを並べて照合してから切り替える、E-B3 削除の印が消える前に受け手が追いつくことを監視 | オンラインスキーマ変更の専用の道具は見送り |
| C | E-C1 列指向と圧縮、E-C2 取り込み時にスキーマを決める列と、後から読む列を分ける、E-C3 保持期間で古いデータを落とす | 全文検索の専用ストアは見送り |
| D | E-D1 必要な箇所だけ Serializable にして再試行する、E-D2 明示的なロック／バージョン列、E-D3 昇格の前に旧プライマリを遮断する手順 | 全トランザクションの Serializable 化は見送り候補（再試行の回数と遅さを測って判断） |

## 3. 題材 A：基盤をまたぐデータ統合

**問い**：注文の状態の変化を、検索の索引と通知へ、失わず・重複させず・順序を崩さずに届けられるか。

| 構成 | 作り |
| --- | --- |
| N | 二重書き込み：注文サービスが DB を更新し、続けてブローカーへ発行する（別々の操作） |
| B | アウトボックス＋ポーリング：同じトランザクションでアウトボックスの表に書き、別のプロセスが読んで発行。受け手は冪等 |
| BE | アウトボックス＋CDC（Debezium）：WAL からアウトボックスの行を読んで発行。キーごとの順序、WAL の上限、照合 |

**ケース**（各ケースに ID・狙い・ガイドの Part。正常と障害を混ぜる）

| 群 | 内容 | 例 |
| --- | --- | --- |
| A-正常 | 障害なし。直列の更新、並行の更新（同じ注文を 2 つの書き手が更新） | 並行度 1・4・16 |
| A-書き手の障害 | DB の更新と発行の間で書き手を強制終了、発行の途中でブローカーへの接続を切る | 決まった件数目で kill |
| A-ブローカーの障害 | ブローカーの一時停止・再起動、遅延 | Toxiproxy で切断、Pumba で pause |
| A-受け手の障害 | 処理の途中で受け手を強制終了、受け手を長く止める | 再起動後の重複、WAL の増え方 |
| A-運び手の障害 | ポーリングのプロセス／Debezium の強制終了と再起動 | 再送による重複、読み飛ばし |

**測るもの**：欠落（応答済みなのに届かない）、重複（受け手に 2 回以上届いた／受け手の状態に 2 回効いた）、順序のずれ（キーごと）、最終状態の食い違い（正と導出の差）、正常時の遅れ（p50・p95）、CDC の受け手を止めたときの WAL の大きさの時間変化。判定は書き手 ID＋連番と、DB の最終状態で行う。

**除去**：B − 冪等な受け手／B − アウトボックス（＝二重書き込みに戻す）／BE − キーごとの順序／BE − WAL の上限／BE − 照合。**変種**：ポーリングで「まだコミットされていない小さい連番」を読み飛ばす作り（よくある誤り）。

**照合**：Redpanda で測ったあと、欠落と重複のケースを Apache Kafka でも流し、結果が同じかを見る（題材 A の一部だけ）。

## 4. 題材 B：置換と更新の演習

**問い**：動かしたまま、スキーマを変え、導出ストアを入れ替え、ログから作り直せるか。

| 実験 | 構成 | 測るもの |
| --- | --- | --- |
| B-1 イベントのスキーマ変更 | N：検査なしで配る／B：互換性検査（直前の版とだけ比べる既定）／BE：推移的な検査。新旧の書き手と受け手を混在させる（逐次更新） | 壊れた受け手の数、黙って誤った値になった受け手の数、検査で止められた変更の数。**正常な変更（任意フィールドの追加）が誤って止められないか** |
| B-2 古いデータの読み直し | v1 → v2 → v3 と各段は検査を通るが、v3 の受け手が v1 のデータを読めない変更の列を作る | 既定（非推移）で通ってしまうか、推移的な検査で止まるか、再構築で失敗する件数 |
| B-3 DB のスキーマ変更 | N：1 回の ALTER で型や制約を変える／BE：expand-contract。書き込みの負荷をかけ続ける | 書き込みが止まった時間、ロック待ちの数、失敗した要求の数。PostgreSQL 18 の操作ごとのロックと書き換えの有無の表（公式文書にまとまった表が無いため実測） |
| B-4 導出ストアの入れ替え | ログ（イベント）から新しい導出ストアを作り、旧と照合して切り替える | 再構築の所要時間、旧との一致率、切り替え中に失われた更新の数 |
| B-5 作り直しの前提条件 | 保持期間・コンパクション・削除の印（tombstone）の設定を変え、既定のままログから再構築する | 再構築できたか、削除が落ちた件数（削除の印が消えた後に受け手が追いついた場合）、消えたはずのデータが導出側に残る件数 |
| B-6 記録のシステムの入れ替え | PostgreSQL から別のインスタンスへ、並行稼働・照合・切り替え・切り戻しの窓の 6 段階で移す（ガイド Part 15 の「本ガイドの考え」） | 各段階での失敗数、書き込みが止まった時間、切り戻したときに失われる書き込みの数 |

**除去**：BE − 推移的な検査／BE − 冪等な受け手（再構築の重複）／BE − 照合（切り替え）／BE − スナップショット（保持期間を過ぎたログからの再構築）。

## 5. 題材 C：共通基盤の費用と性能

**問い**：ログ基盤・分析基盤で、どの持ち方が何を払うか。

| 実験 | 比べるもの | 測るもの |
| --- | --- | --- |
| C-1 行指向と列指向 | PostgreSQL（行）／ClickHouse（列）／DuckDB＋Parquet（ファイル）。同じデータ、同じ問い合わせ | 容量、取り込み時間、問い合わせ時間（点の検索、範囲、集計、上位 N）。各 5 回の中央値と幅 |
| C-2 取り込み時スキーマと読み出し時スキーマ | 列に分けて入れる／JSON のまま入れる（PostgreSQL の jsonb、ClickHouse の JSON 型、DuckDB の read_json） | 容量、問い合わせ時間、**スキーマが揺れたとき（型が変わる、フィールドが消える・増える）の失敗の出方**：取り込みで止まるか、黙って NULL になるか、問い合わせで落ちるか |
| C-3 保持と圧縮 | 保持期間、圧縮の方式、並び順 | 容量の変化、古いデータを落とす操作の時間 |
| C-4 冪等な再実行 | 同じ範囲のバッチを 2 回流す（INSERT／置き換え） | 重複の件数 |
| C-5 索引の費用 | 索引を足す前後 | 書き込みの時間、容量、読み取りの時間 |

データ：公開の小さなデータセット（数百 MB 以下）と、生成器で作るログ。**同じ環境の中での相対比較**で、公式のベンチマークの結果とは比べない。B ツリーと LSM ツリーの直接比較はしない（ガイドに明記済み）。

## 6. 題材 D：整合性の異常の再現

**問い**：どの設定が、どの異常を許し、何を失うか。同じ名前の設定で、製品ごとに結果が違うか。

| 実験 | 構成 | 測るもの |
| --- | --- | --- |
| D-1 分離レベルごとの異常 | PostgreSQL 18・MySQL・CockroachDB で、各製品が持つ分離レベル。Hermitage の手順（2 つのセッションの実行順を固定）で、ダーティリード、ロストアップデート、リードスキュー、ライトスキュー、ファントム | 異常が起きたか（製品 × 水準 × 異常の表）。ガイドの Part 9 の表（文献による）と照合し、食い違いを記録 |
| D-2 並行の負荷での発生率 | 在庫の引き当て（読んで、計算して、書く）を並行度を変えて実行 | ロストアップデートの件数、最終の在庫数のずれ、Serializable での再試行の回数と所要時間 |
| D-3 防ぎ方の費用 | アトミックな更新／SELECT FOR UPDATE／バージョン列／Serializable＋再試行／制約 | 異常の件数、処理できた件数、p50・p95、再試行の回数 |
| D-4 同期と非同期の複製 | PostgreSQL のプライマリ＋スタンバイ。synchronous_commit と synchronous_standby_names の組み合わせ | プライマリを強制終了してスタンバイを昇格したとき、**応答済みなのに失われたコミットの件数** |
| D-5 損失ゼロの設定の費用 | 同期の設定で、スタンバイを止める | 正常な書き込みが止まるか、待ち続けるか（時間を区切って観測）、書き込みの遅さ |
| D-6 古い読み取り | レプリケーションを遅らせ、書いた直後にスタンバイから読む | 自分の書き込みが読めない割合、remote_apply での変化 |
| D-7 昇格の手順 | 旧プライマリを遮断せずに昇格／遮断してから昇格 | 両方に書けてしまった件数（スプリットブレイン） |

**除去**：BE − 同期の複製／BE − 再試行／BE − 明示的なロック／BE − 遮断。MySQL の Repeatable Read は、文献（Hermitage・Jepsen 8.0.34・ACIDRain）が一致するのは「ロストアップデートを防がない」点だけなので、それ以外は実測の結果をそのまま書く。

## 7. 環境と進め方

| 項目 | 方針 |
| --- | --- |
| 実行場所 | WSL2（Ubuntu-24.04）の中の Docker Engine。Docker Desktop は使わない |
| 製品と版 | PostgreSQL 18、MySQL（8.4 系）、Redpanda、Apache Kafka 4.x、Debezium 3.7、ClickHouse、DuckDB、CockroachDB。**着手時にタグとダイジェストを確かめて固定し、結果に記録する** |
| 同時に動かす量 | 題材ごとにコンテナを上げ下げし、同時に動かすのは約 3 GB まで。ほかのプロジェクトのコンテナには触れない |
| 障害の入れ方 | Toxiproxy（切断・遅延）と Pumba（強制終了・一時停止）。確率的な障害は使わず、件数を合図に入れて外す |
| 決定性 | 乱数の種を固定、順序は連番と LSN で判定、毎回ボリュームを消して最初から。並行の競合に頼る実験（D-2 など）は、種・試行回数・発生率をセットで報告する |
| 耐久性の設定 | 欠落を数える実験では、Redpanda を開発モード（fsync を省く）で動かさない |
| 再開 | 実験ごとに結果を 1 行ずつ JSONL に追記し、完了済みを飛ばして再開できるようにする |
| 記録 | 環境（CPU、メモリ、製品の版、イメージのダイジェスト）、所要時間、ケースごとの生の結果、`results/summary.md` |
| 採点の監査 | 欠落・重複・順序の判定器に、誤りを仕込んだデータ（わざと欠落・重複・逆順を入れた列）を流し、正しく数えるかを確かめる |
| 片付け | 題材ごとにコンテナとボリュームを消し、残りが無いことを確かめる |

**測れないこと**（結果にも明記する）：クラウドのマネージド製品、リージョンをまたぐ障害、時計のずれに由来する異常（1 台の上では時計が共有される）、大きな規模での性能（1 台・小さなデータでの相対比較にとどまる）。

## 8. 進める順番

1. 共通の土台（生成器、判定器と監査、コンテナの起動と待機、障害の注入、結果の記録）
2. 題材 D（PostgreSQL だけで始められ、最も軽い）→ MySQL・CockroachDB を足す
3. 題材 A（Redpanda・Debezium）→ Apache Kafka での照合
4. 題材 B（題材 A の構成を使い回す）
5. 題材 C（ClickHouse・DuckDB）
6. 結果のまとめ、スライド、ファクトチェック
7. ガイドの該当スライドへ結果を戻す、設計レビューの一覧表

題材が 1 つ終わるごとに、結果の要点と、ガイドの記述と食い違った点を報告する。

## 10. 設計から変えた点（実験の後に追記）

上の 1〜9 節は、実験の前に書いた設計のままである。実際に流した実験は、次の点で設計と違う。結果は `results/<題材>/summary.md`、2 回の実行の比較は `results/RERUN.md` にある。

| 項目 | 設計 | 実際 |
| --- | --- | --- |
| 障害の入れ方（7 節） | Toxiproxy（切断・遅延）と Pumba（強制終了・一時停止） | Pumba は使っていない。経路の切断と遅延は Toxiproxy、強制終了・一時停止・停止は `docker kill`・`docker pause`・`docker stop` を、件数を合図に呼んだ。題材 C は Toxiproxy も使わず、下流の 503 応答と `docker kill`・`docker pause` で入れた |
| 題材の世界（1 節） | 注文・在庫・決済・通知の 4 つの業務サービスを、それぞれ記録のシステムつきで持つ | 決済（payments）のサービスと DB は組んでいない。決済は、題材 C のログの項目（payment_method）として出てくるだけである。通知は、題材 A のイベントの受け手として組んだ |
| 題材 B の実験（4 節） | B-1〜B-6 | B-7（マテリアライズドビューが追随するもの：PostgreSQL の REFRESH、ClickHouse の増分・refreshable）を足した。ガイドの Part 12 が「題材 B で実測する」と書いた点に当たる |
| 題材 C の実験（5 節） | C-1〜C-5 | C-6（Collector の送信で、まだ失う場面）を足した。ガイドの Part 13 のテレメトリの記述に当たる |
| 題材 C の構成 B（2 節） | 共通の基準 B1〜B6 のどれか | 題材 C の B は「再実行しても同じ結果になる取り込み」（C-4）で、B1〜B6 のどれにも当たらない。題材 C の構成は、1 本の流れを組み替えたものではなく、実験ごとの選択の組み合わせである |
| 題材 C のデータ（5 節） | 公開の小さなデータセットと、生成器で作るログ | 公開のデータセットは使っていない（正解を生成器から作れないため）。生成器のログだけで測った |
| 題材 D の構成（2・6 節） | N・B・BE | D-1〜D-7 は要素を 1 つずつ変えた実験で、N・B・BE を通しで流した実行は無い。対応は題材 D の summary の「除去実験」の表 |
| 実行の回数 | 1 回 | 4 題材とも、同じコードで最初から 2 回流した。並行の競合や時間に頼る結果は 2 回で変わったものがあり、summary は 2 回の値を並べている |
| 成果物（9 節） | `run_all.py`、`results/summary.md` | 通しのスクリプトは題材ごとの `cs/<題材>/run.sh`。まとめは題材ごとの `results/<題材>/summary.md` と `results/RERUN.md` |
