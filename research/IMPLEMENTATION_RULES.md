# 実験の実装の担当への規則

ケーススタディの設計は [DESIGN.md](DESIGN.md)。この文書は、どの題材の実装にも共通の決まり。

## 環境

- Docker は **WSL2（Ubuntu-24.04）の中の Docker Engine** を使う。Windows 側から呼ぶときは `MSYS_NO_PATHCONV=1 wsl -d Ubuntu-24.04 -- bash <スクリプトの /mnt/ パス>`。Docker Desktop は使わない
- 数行を超えるコマンドは、リポジトリにシェルスクリプトとして置いてから呼ぶ（引用符の入れ子で壊れるため）
- WSL の中では sudo を使えない。Python は `uv` か venv（WSL のホームの下。例：`~/dic-cs/.venv`）で用意する。コードと結果はリポジトリ（Windows 側のドライブ、WSL からは `/mnt/` 以下）に置く
- **DB のデータは名前付きボリュームに置く**（Windows 側のドライブへのバインドマウントは遅い）
- コンテナ・ネットワーク・ボリュームの名前は必ず `dic-` で始める。**`dic-` で始まらないコンテナ・イメージ・ボリュームには一切触れない**（ほかのプロジェクトのものが動いている）。`docker system prune` などの一括の掃除はしない
- ホストに公開するポートは 25000〜25999 の範囲だけを使う
- イメージは、着手時に公式の配布元でタグを確かめ、pull したあと `docker image inspect` のダイジェストを `results/env.json` に記録する。compose ではタグを固定する（`latest` を使わない）

## メモリとディスク

- 実験の前と、長い実験の途中に、Windows の空きメモリを確かめる：`powershell -NoProfile -Command "[math]::Round((Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory/1MB,1)"`（単位 GB）。**3 GB を切ったら、実験のコンテナを止めて、取りまとめ役に報告して終わる**（勝手に再開しない）
- 同時に動かすコンテナは合計で約 3 GB まで。DB には小さめのメモリ設定を入れる
- 実験が 1 つ終わるごとに `dic-` のコンテナとボリュームを消し、残りが無いことを確かめる
- pull の前に、追加で使うディスクの見込みを確かめる（イメージの合計は 5 GB 以内を目安）

## 測り方

- **決定的に流す**：乱数の種を固定する。順序は書き手 ID＋連番と LSN・オフセットで判定し、壁時計の時刻に頼らない。毎回ボリュームを消して最初から始める
- 並行の競合に頼る実験は、種・試行回数・発生率をセットで記録する。1 回の結果で断定しない（試行は 5 回以上、できれば 20 回以上）
- **正解は生成器から作る**（どの操作が成功したと応答されたか、最終状態はどうあるべきか）。実験の出力から正解を作らない
- **最終状態で判定する**：ログやメッセージの文言ではなく、DB と導出ストアの最終状態で判定する
- **判定器を監査する**：欠落・重複・順序・異常の判定器に、誤りを仕込んだデータ（わざと欠落・重複・逆順・異常を入れた列）と、誤りの無いデータを流し、正しく数えることを確かめる。監査の結果も `results/` に残す
- **正常な操作も数える**：基準や重点を入れた構成で、正規の処理が失敗・遅延・停止していないかを必ず数える
- 遅延は p50・p95 と回数を書く。性能は同じ環境の中での相対比較で、絶対値を一般化しない
- 障害は、件数を合図に入れて外す（確率的な障害は使わない）。入れた時点と外した時点を記録する

## 記録

- 結果は 1 回の実行を 1 行の JSONL に追記する（実行 ID、構成、ケース、種、入力の規模、生の数、所要時間、製品の版）。完了済みの実行 ID は飛ばして再開できるようにする
- `results/env.json`：CPU、メモリ、OS、Docker の版、製品の版、イメージのダイジェスト、実行日
- `results/<題材>/summary.md`：構成 × ケースの表、除去実験の表、測定値、ガイドの記述と食い違った点、限界、測れなかったこと。**表の数は必ず結果のファイルから数えて書く**（手で書かない。集計のスクリプトを置く）。表に空欄を残さない
- 測っていないことは「未検証」と書く。期待どおりにならなかった結果も、隠さずそのまま書く（原因が分かれば原因も）

## コード

- `cs/common/`：生成器、判定器、コンテナの起動と待機（準備できるまで待ち、失敗ならログを出す）、障害の注入、結果の記録
- `cs/<題材>/`：compose の定義、実験のスクリプト、`run.py`（その題材を最初から最後まで流す）
- 試験用のパスワードは固定値でよい（コンテナの設定に書いてよい）。鍵は置かない
- 公開するリポジトリなので、手元のパス（ドライブ名から始まるパス、ホームのパス）をコードや結果に書かない。パスは相対か、環境変数で受ける
- コメントは英語でよい。文書（summary など）は日本語で、ガイドの訳語（記録のシステム、導出データ、ロストアップデート、ライトスキュー、逐次更新）に揃える

## してはいけないこと

- ガイドのリポジトリ（`data-intensive-design-guide`）のファイルを編集しない（読むのはよい）
- git の commit・push をしない（取りまとめ役が行う）
- 実験の結果を、ガイドの記述に合うように調整しない。食い違ったら、食い違いとして報告する
