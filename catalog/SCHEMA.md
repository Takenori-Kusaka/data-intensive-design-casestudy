# 設計レビューの問いの一覧：行と列の定義

`data-intensive-design-review.xlsx` のシート「一覧」の定義。値の集合は `scripts/view.py` の定数が正で、`scripts/validate.py` が検査する。

## 行にするもの

1 行は 1 つの問い。ガイドとケーススタディに**問いの形で書いてあるもの**だけを行にする。

| 出どころ | 拾い方（`scripts/collect_guide.py` の SPEC） |
| --- | --- |
| 各 Part の「設計レビューで問うこと」のスライド（Part 1〜16） | 表の「問い」「なぜ問うか」「危ない兆候」の列をそのまま |
| Part 3「分ける理由 6 つと、まとめる理由 2 つを並べる」 | 2 つの表の「問い」の列。要因の名前は備考へ |
| Part 11「サーガは 3 つの軸で整理し、調整役の得失で選ぶ」 | 1 つ目の表の「問うこと」の列 |
| Part 12「導出データにも出力の検査が要る：照合と系譜」 | 「答える問い」の列 |
| Part 13「共通基盤は内部の利用者に出す製品。作る前に問う」「どの基盤も、同じ 4 つの問いで設計する」 | 表の問いと、4 枚のカードの題 |
| Part 14「設計レビューで問うこと：型ごとに 1 問」 | 表の問い。概観の表「被害を広げた設計は、8 つの型にまとまる」の「問うこと」は短い形なので、同じ番号の行にまとめる |
| Part 17 | 9 つのステップの「答える問い」（Part 0 の同じ表とまとめる）、ADR に足す 3 項目、トレードオフの分析の問い 1 つ。「まず問うこと」「4 つの性質」「節目」の表は各 Part の問いの引用なので、元の行にまとめる |
| ケーススタディの「設計レビューに持ち帰る問い」（Part 1〜5 の 5 枚） | 表の問い、またはカードの題（`scripts/collect_casestudy.py`） |

行にしないもの：

- 各 Part の扉の「この Part で答えられるようになる問い」（読者が学ぶ問いで、設計に向ける問いではない）
- 問いの形でない表（「確かめ方」「提案に書くこと」「製品ごとに確かめること」など）。内容は、関係する行の「よい答えの例」に使う
- ステップ × 基盤の掛け合わせ。Part 13 の「7 基盤 × 4 つの問い」の表は答えの表なので、4 つの問いの行（RQ-P13-04〜07）の「よい答えの例」に使い、28 行にはしない

## まとめ方

1. **文言が同じ問いは 1 行**（空白と改行を除いて比べる）。Part 17 と Part 0 は各 Part の問いを文言のまま引いているので、元の Part の行にまとめ、「ガイドのスライド」に出どころを全部書く
2. Part 14 の概観の表の短い形は、同じ番号（①〜⑧）の行にまとめる
3. 文言が違えば、似ていても別の行（例：RQ-P05-01 と RQ-P12-05）。備考に相手の ID を書く
4. ケーススタディの持ち帰る問いは、ガイドの問いと**同じ決定を問う**ならその行にまとめ、無ければ別の行にする。判断は `raw/casestudy_map.json` に 1 問ずつ理由つきで書く。別の行にした問いは、出どころの種別が「ケーススタディから持ち帰る問い」

## ID

- ガイドの問い：`RQ-P<Part 2 桁>-<その Part のスライドでの出現順 2 桁>`（Part 13 は p13・p13b を通しで数える）
- ケーススタディだけの問い：`RQ-C<A〜D>-<その題材の持ち帰る問いのスライドでの順 2 桁>`
- スライドの表の順が変わらない限り、ID は変わらない

## 列

空欄を許すのは記入欄の 5 列だけ。ほかは全行を埋め、当たらないときは「該当なし（理由）」「実測なし（理由）」「測っていない（理由）」と書く。

### 定義

| 列 | 中身 | 値・書き方 |
| --- | --- | --- |
| No | 表の中の通し番号 | 1〜 |
| ID | 上の規則 | |
| ステップ | ガイドのスライドのタグ | 全体（Part 1・17）／1 要件／2 所有／3 モデル／基礎（Part 5・10）／4 流れ／5 契約／6 複製／7 正しさ／8 導出／9 基盤／置換と更新（Part 15）／責任（Part 16）。Part 17 の 9 つのステップの問いは、そのステップ。ケーススタディだけの問いは、関連するガイドのスライドのステップ |
| 対象 | その問いを向ける先。1 つだけ | サービス全般／共通基盤全般／データ基盤／ETL 基盤／ログ基盤／認証基盤／AI 基盤／分析基盤／セキュリティ基盤。既定は、Part 13・14 が共通基盤全般、ほかはサービス全般。基盤を名指しした問いだけ、その基盤 |
| 問い | スライドの文のまま | |
| なぜ問うか | スライドの表の文のまま。欄が無い行は補う（下の「補った欄」） | |
| よい答えの例 | その Part のスライドの題・リード・表・ノートに書いてある推奨を、1〜2 文にまとめたもの | スライドの文そのものではなく、この表の作成時にまとめた。ガイドに無い助言は足さない |
| 危ない兆候 | スライドの表の文のまま。欄が無い行は補う | |
| いつ問うか | 作る前／動かす前／変更の前／入れ替えの前／やめる前／定期 | 「・」で並べる。Part 17 の「基盤は、作る前・入れ替える前・やめる前に問う」が節目を挙げた問いは、その節目を必ず含む。ほかは、この表の作成時に付けた |
| まず問う問いか（Part 17） | Part 17 の「まず問うこと」の 3 枚の表に選ばれた問いか | はい（スライドの題）／いいえ（理由） |
| 4 つの性質のどれに効くか | 柔軟性／拡張性／置換性／更新性 | 「性質・性質：効く理由を 1 句」。Part 17 の「4 つの性質から、効くステップと問いを引く」が挙げた問いは、その性質を必ず含む。ほかは、この表の作成時に付けた |

### 根拠

| 列 | 中身 | 値・書き方 |
| --- | --- | --- |
| 根拠の種別 | スライドの根拠の行にある種別 | 仕様・文書／指針・報告／書籍／本ガイドの考え／ケーススタディの実測。「／」で並べる。「なぜ問うか」「危ない兆候」をこの表で補った行、根拠の行が本ガイドの構成の説明だけの行は「本ガイドの考え」を含む。ケーススタディだけの問いは「ケーススタディの実測」 |
| 根拠 | 問いが載っているスライドの根拠の行の写し | 問い 1 つずつの出典ではなく、スライド 1 枚の根拠。原典の名前・節・版・確認月は、スライドの書き方のまま |
| 書籍 | 根拠の行の「書籍」の部分 | 書名・章節・印刷ページだけ。本文は引用しない。無ければ「該当なし（ガイドのスライドに書籍の根拠なし）」 |
| ガイドのスライド | Part・題・スライド番号。まとめた出どころを全部 | 1 つ目のスライドへ、Web 版のリンク（`…/data-intensive-design-guide/#s<番号>`）。ケーススタディだけの問いは「ガイドの問いの表には無い。関連するスライド：…」（照合の表が挙げたスライド） |

### 実測

| 列 | 中身 | 値・書き方 |
| --- | --- | --- |
| 題材と実験 | 題材 A〜D と実験の ID・名前 | 無ければ「該当なし（理由）」 |
| 実測の結果 | summary から写した数。この表の作成時に要約した | 2 回で違えば「1 回目 a・2 回目 b」。0 件には試行の数。原因を調べていないことは、そう書く |
| 実測の判定（区分） | 右の列の判定の、かっこの前の語 | 結びつけた照合の行の区分が 1 種類ならその語、2 種類以上なら「複数の判定（右の列）」、結びつく行が無ければ「実測なし（未検証）」。集計のための列 |
| 実測の判定（照合の表のまま） | `results/<題材>/summary.md` の「ガイドの記述との照合」の行の判定を、行の番号（A-01 など）つきでそのまま | 強調の記号（`**`）だけ除く。結びつく行が無ければ「実測なし（未検証）」 |
| 結果へのリンク | summary のファイルと節の名前、照合の行の番号 | GitHub の該当の節へリンク |
| ケーススタディのスライド | この問いを持ち帰る問いとして載せたスライドと、その文。続けて、結びつけた照合の行のガイドのスライドを根拠の行に挙げているケーススタディのスライド（3 枚まで） | 無ければ「該当なし（理由）」 |

照合の行の番号は、summary の表の上からの順（`scripts/extract_casestudy.py`）。全 152 行と、結びつけた問いは、シート「照合の行」にある。

### 架空の宅配注文サービスでの扱い

判定の値と付け方は [DECISION_POLICY.md](DECISION_POLICY.md)。

| 列 | 中身 |
| --- | --- |
| 扱いの判定 | 共通の基準に含めた／題材の重点に含めた／実験で比べた／見送った／測っていない／対象外 |
| 理由（防いだこと／失うこと） | 入れたもの：外したときに再び壊れた数（除去実験）。見送ったもの：失うもの。測っていない・対象外：何を組んでいないか、この表から何が言えないか |
| 正常な操作への費用 | 所要時間、失敗した要求、遅れ、再試行、保存域など。実測が無ければ「測っていない（理由）」 |
| 見直し条件 | 判断を変える条件、または未検証の範囲に入る条件 |

### 記入欄（自分のシステム）

空のまま配る。検査は「空であること」だけ。

| 列 | 書くこと |
| --- | --- |
| 自分のシステムでの現状の答え | 問いへの答えを、数字と記録で |
| 判定 | 問題なし／要対応／対象外（入力規則つき） |
| 担当・期限・メモ | 自由に |

### 備考と確認

| 列 | 中身 |
| --- | --- |
| 備考 | スライドの表での見出し（要因、型の番号、基盤など）、まとめた問いと理由、Part 17 が性質・節目に選んだこと、補った欄、近い問いの ID。何も無ければ「特記なし（理由）」 |
| 確認日 | ガイドのスライドと summary を読み直した日 |
| 出どころの種別 | ガイドの問い／ケーススタディから持ち帰る問い／両方（ガイドの問い＋ケーススタディから持ち帰る問い） |

## 補った欄

スライドの表に「なぜ問うか」「危ない兆候」の欄が無い問いがある（Part 3 の要因の問い、Part 11 の軸の問い、Part 12 の道具の問い、Part 13 の 4 つの問い、Part 17 の問い、ケーススタディの問い）。これらは、**同じスライドのリード・ノート・隣の列**から補い、文の中に出どころ（「同じスライドのリード」など）を書いた。ケーススタディの問いの「なぜ問うか」は、スライドの「この実測での裏づけ」の列をそのまま使い、「危ない兆候」は実測で壊れた作りから書いた。補った行は、根拠の種別に「本ガイドの考え」（ケーススタディの問いは「ケーススタディの実測」）が入り、備考に補った欄の名前が出る。

## 最初の案から変えた列

| 変えたこと | 理由 |
| --- | --- |
| 対象は 1 列・1 値にし、基盤ごとの ○／— の列は作らない | 基盤を名指しした問いは Part 13 の 7 行ほどで、7 列 × 全行の ○／— は掛け合わせで埋めることになる（根拠の無いセルを作らないという決めに反する） |
| 「まず問う問いか（Part 17）」を足した | Part 17 が、ステップごとに最初に問う 1〜2 問を選んでいる。新任のリーダーが最初に絞り込む列になる。スライドから機械的に取れる |
| 「実測の判定」を 2 列にした（照合の表のまま／区分） | summary の判定は、かっこの中に条件を書いた文で、そのままでは数えられない。写しの列は 1 字も変えず、数えるための区分を別の列にした |
| 根拠の種別に「ケーススタディの実測」を足した | ケーススタディだけにある問いは、ガイドのスライドの根拠の行を持たない |
| 出どころの種別に「両方」を足した | ガイドの問いにまとめた持ち帰る問い（16 行）が分かるようにする |
| 扱いの判定に「実験で比べた」を足した | 基準にも重点にも入れていないが、実験で比べて数字がある問い（分離レベルの既定、索引、マテリアライズドビューなど）を、「測っていない」と区別する |
