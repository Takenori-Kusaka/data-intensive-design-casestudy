# データ指向で設計する大規模クラウドサービス ― ケーススタディ（実測）

ガイド [data-intensive-design-guide](https://github.com/Takenori-Kusaka/data-intensive-design-guide)（新任のテックリーダー向けのスライド）の主張を、手元の 1 台（WSL2 の Docker）で確かめた記録。1 つの架空の宅配注文サービス（業務サービスと共通基盤）の上で 4 つの題材を測り、結果を「ガイドの記述との照合」の表にまとめた。

会社・サービス・数値はすべて架空で、実在の組織のシステムとは関係がない。性能の数字は、同じ機械・同じデータの中での相対比較で、ほかの環境には一般化できない。

- 2 回の実行の比較：[results/RERUN.md](results/RERUN.md)
- 実験の設計：[research/DESIGN.md](research/DESIGN.md)（末尾に「設計から変えた点」）、実装の決まり：[research/IMPLEMENTATION_RULES.md](research/IMPLEMENTATION_RULES.md)
- スライド（`slides/`・`docs/`）と設計レビューの一覧表（`catalog/`）：準備中

## 主な結果

題材ごとの summary の要点を写したもの。数は、断りが無ければ 2 回とも同じ値。2 回で違った数は「1 回目 → 2 回目」と並べた。「0 件」は、この手順と試行の数で起きなかったという意味で、起きないことの証明ではない。

**題材 A（基盤をまたぐデータ統合）**

- 二重書き込みは、障害を入れなくても順序が入れ替わった。並行度 16 で 5 組（4/5 試行）→ 11 組（5/5 試行）、並行度 4 で 0 組 → 1 組（1/5 試行）。エラーは返っていない。Redpanda での最終状態の食い違いは 2 回とも 0 で、残るかどうかは試行による
- 二重書き込みで書き手を強制終了すると、DB にコミット済みなのに索引に届かないイベントが 14 件 → 16 件。アウトボックスの 2 つの構成では 0 件
- 冪等な受け手を入れた構成の全 85 実行で、受け手の状態に 2 回効いたイベントは 0（届いた重複は 1551 回 → 1746 回）。Kafka のトランザクションは使っていない
- 「最後に読んだ連番より大きい行だけ読む」ポーリングは、応答済みのイベントを読み飛ばした。並行度 4 で 12 件（5/5 試行）→ 1 件（1/5 試行）、並行度 16 で 76 件 → 85 件（どちらも 5/5 試行）
- Debezium を止めたまま書き続けると、既定ではスロットが保持する WAL が増え続けた。上限（64MB）を付けるとスロットが無効になり、止めている間に書いた 800 件（試行ごと）が届かなかった

**題材 B（置換と更新の演習）**

- スキーマレジストリの既定（BACKWARD）は、段ごとには通るが v3 の受け手が v1 のデータを読めない変更の列を、3 形式とも通した。BACKWARD_TRANSITIVE は v3 の登録を拒否した
- 列を分ける変更を 1 つのトランザクションで行うと、失敗した要求が 195 件 → 189 件（5/5 試行）。expand/contract では 0 件（5 試行）で、所要時間は延びた
- 導出ストアを同じ場所で作り直すと、読み取りで見つからない 1222 件 → 1296 件。新旧を並べて照合してから切り替えると 0 件。ただし、切り替えの途中に前より古い版を読んだ読み取りが 0 件 → 1 件（1/5 試行）あり、この行の判定は「実行によって変わった」
- 二重書き込みでの記録のシステムの移行では、埋め戻しの後に新が古い・無い行が残った（1 試行あたり 5.8 件 → 5.0 件）。版を比べる埋め戻しでも残り（3.2 件 → 4.8 件）、減ったとは言えない。理由は調べていない

**題材 C（共通基盤の費用と性能）**

- 3,000,000 行の容量は、PostgreSQL 718.4 MB、ClickHouse 220.1 MB、DuckDB＋Parquet 169.7 MB。キーで 1 行の検索は行指向が短く、店舗ごとの集計は列指向とファイルが短い（大小は 2 回とも同じ）
- スキーマが揺れたとき、製品の既定の取り込みは、止まる・黙って落とす・黙って 0 や NULL で埋める、と製品と取り込みの作りで分かれた（揺れのある 117 実行。内訳は summary）
- PostgreSQL に索引を 1 本足すと、絞り込みは 2 桁短くなり、一括の取り込みは 1.59 倍 → 1.60 倍になった。一部の列を中に持つ索引の読み取りの差、ClickHouse のスキップ索引と DuckDB の索引の効果は、問い合わせの形で向きが違い、試行の範囲が重なるものは差を言えない
- Collector の送信では、メモリのキューでもディスクのキューでも、再試行の時間切れで受け付け済みのログを失った。Kafka を間に置いても、読む側の Collector が既定のままだと強制終了で失った。ブローカーを一時停止して戻しただけの場面は、1 回目は失わず（0/3 試行）、2 回目は 1/3 試行で 20 件を失った（原因は特定していない）

**題材 D（整合性の異常の再現）**

- 分離レベルごとの異常は、Hermitage の表（PostgreSQL・MySQL・CockroachDB の 100 セル）と食い違わなかった。MySQL 8.4 の Repeatable Read は、並行の負荷でロストアップデートを 2449 件 → 2417 件（応答済み 6000 件）起こし、PostgreSQL の Repeatable Read は 0 件
- PostgreSQL は、synchronous_commit = on でも同期スタンバイを名指ししないと、経路を切った後に応答した 600 件を昇格で失った。名指しすると 0 件で、代わりに、同期スタンバイを止めると書き込みは観測の時間（15・60 秒）の間は返らなかった（12 試行）
- 経路を切らずに強制終了した場合に失う件数は、強制終了の瞬間に左右される。名指しなし・on は 2 回とも 0 件、名指しなし・local は 3 件（1/5 試行）→ 0 件。0 件は失わない設定という意味ではない
- 遮断せずに昇格すると、旧プライマリが昇格後も 300 件に応答し、同じ ID で中身が違う行が 204 件できた。遮断すると 0 件

## ガイドと食い違った点・条件を足す点

4 つの照合の表（A 16 行、B 53 行、C 42 行、D 41 行）に、無条件の「食い違い」と判定した行は無い。条件が付いた行と、2 回で判定が変わった行は次のとおり。

- A「遅れ：CDC は書き込みの直後に流せる」：条件つきで食い違い。並行度 1 の遅れの p50 は、ポーリング（間隔 50 ms）が 19.4 ms → 17.2 ms、CDC（Debezium の poll.interval.ms は既定の 500 ms）が 691.2 ms → 699.6 ms。間隔を変えた CDC は測っていない
- B「Protocol Buffers：削除も安全」：条件つき。受け手が使うフィールドを消すと、全モードで登録が通り、エラーも無く、値が既定値で黙って埋まった
- B「並べて切り替えれば…」と、それを指す 1 行：実行によって変わった（上の題材 B の 3 点目）
- C「Kafka を間に置く：下流が戻るまで Kafka にたまる」：条件つき。読む側の Collector が既定のままだと、先に読み出して自分のメモリに持ち、強制終了で失った
- C「Kafka を間に置いても、まだ失う場面は…」：2 回とも一致だが、ブローカーを戻しただけの場面の欠落の有無が 2 回で違った
- D「remote_apply のコミットの遅れは、ほかの値よりずっと大きい」：条件による。適用が遅れない条件では on と差が出ず、適用を 200 ms 遅らせた条件では、その分だけ増えた

## 2 回の実行と RERUN.md の読み方

- `results/<題材>/*.jsonl` が 2 回目、`results/<題材>/run1/*.jsonl` が 1 回目。実行 ID の集合は 2 回で同じ
- summary の数は、断りが無ければ 2 回目。1 回目と違った件数・判定・文は 2 回ぶんを並べてある。**表の中の時間と大きさは 2 回目の値だけ**で、1 回目と違った列は列名に「（2 回目）」と付けてある
- [results/RERUN.md](results/RERUN.md) は、題材ごとに、(1) 決定的なはずの欄が変わった実行、(2)「起きた／起きなかった」（合計が 0 か 1 以上か）が 2 回で変わった組、(3) 件数と時間の「2 回目 ÷ 1 回目」の比の最小／中央／最大、を並べる
- 並行の競合や、強制終了の瞬間に頼る数は、試行が 3〜5 回と少ない。0 と 1 以上が 2 回で入れ替わった結果は、「起きうるが、起きない試行もある」と読む

## 限界と未検証

- 1 台（8 コア、WSL2 の Docker）の上の、1 ノードの製品と小さなデータ。複製をまたぐ障害、リージョンをまたぐ障害、時計のずれに由来する異常、メモリに収まらない規模は測っていない
- クラウドのマネージド製品は測っていない（ガイドでは公式文書に基づく記述で、未検証と明記している）。認証・AI・セキュリティの各基盤は組んでいない
- 保持の時間（Kafka の 7 日・1 日、Collector の再試行 5 分）は縮めて測った。既定の時間そのものは待っていない
- 電源断に当たる障害（ホストごと落とす）、ディスクが埋まるまでの挙動は試していない
- 原因を調べていない結果がある（題材 A の、スロットを作り直した後に残る食い違い。題材 B の、版を比べる埋め戻しでも残る行。題材 C の、挿入の時間の 2 つの水準と、ブローカーを戻しただけで失った 20 件、など）。summary に「原因は調べていない」と書いてある
- 題材ごとの限界と未検証は、各 summary の末尾にある

## 作り直し方

実験は WSL2（Ubuntu-24.04）の中の Docker Engine で流す。Python は WSL のホームの下の venv（`cs/common/setup_venv.sh`）。Windows 側から呼ぶときは `MSYS_NO_PATHCONV=1 wsl -d Ubuntu-24.04 -- bash /mnt/<ドライブ>/<リポジトリ>/cs/<題材>/run.sh`。

- 題材を流す：`bash cs/<題材>/run.sh`（完了済みの実行 ID は飛ばして再開する。段の指定などは `cs/<題材>/README.md`）。コンテナ・ボリュームの名前は `dic-` で始まり、ポートは 25000〜25999 を使う
- まとめだけを作り直す（実験は流さない。Docker に触れない）：`bash cs/common/remake_summaries.sh`。4 つの summary、`results/RERUN.md`、この README の実行の数の表を、結果のファイルから作り直す
- 検査：`python -m cs.common.check_summaries`（表の空欄と列ずれ、手元のパス、壁時計の時刻、この README の実行の数、照合の表のスライドの題がガイドの題と一致するか）

## 環境と版

AMD Ryzen 7 3700X（8 スレッド）、WSL2 のメモリ 11.7 GB、Ubuntu 24.04.2 LTS、Docker Engine 29.9.2。製品は PostgreSQL 18.7、MySQL 8.4.13、CockroachDB v26.4.0、Redpanda v26.2.7、Apache Kafka 4.4.0、Debezium 3.7、ClickHouse 26.8、DuckDB 2.0.0、OpenTelemetry Collector 0.165.0、Toxiproxy 2.13.0。イメージのタグとダイジェスト、クライアントの版は `results/env.json` と各 summary の「製品の版とイメージ」にある。
